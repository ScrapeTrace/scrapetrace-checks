How this check works

The planter compiles one of two shader programs for each bit. The reader compares the two candidate compile/link times in randomized order. Programs are drawn and pixels read back after the timing interval. A public SHA-256-derived 32-bit tag checks the recovered value. It is an integrity check, not authentication or error correction.

Each run calibrates six new and six repeated programs. Weak separation, unavailable APIs, cancellation and errors remain explicit outcomes. A successful plant confirms compilation completed. Recovery is verified only by a separate reader.

Reading consumes the contrast between the candidates. This tool uses explicit namespaces and banks rather than an automatic visitor identifier or generation search. Different profiles, machines, graphics stacks or worker routing can prevent recovery. A failed read alone does not prove a provider isolates every cache.

Readings stay in the page and local JSON downloads. No result collector is used. Hosting requests still contain the URL parameters, so use random test markers rather than personal information.

For automated runs, wait for #probe-complete[data-status="complete"], then inspect window.__PROBE_RESULT__. Completion includes unsupported, inconclusive and failed outcomes. Allow up to 60 seconds for read and renew, or 30 seconds for a single operation. Completion waits for both stages. Recovery and renewal statuses are reported separately. Use mode=plant, mode=read or mode=read-renew, namespace, bank, and autorun=1. Only the planter accepts marker.
